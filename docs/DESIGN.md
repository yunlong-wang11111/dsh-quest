# 设计取舍 / Design notes

这份文档记录几个"本可以那样、我们选了这样"的决定，以及背后的证据。它不是路线图，是**给未来的自己和评审者看的**：这些地方为什么不做成"更标准"的样子。

## 1. 为什么不用现成的工作流引擎（Airflow / Prefect / Snakemake / Windmill）

quest 的分层里，**调度与 UI 那部分（约一半代码）确实有更强的现成替代**：依赖图、重试、并发、缓存、Web UI 都是这些引擎的成熟领域，Snakemake 的"产物存在且比输入新"几乎就是我们判定器的 `artifact-fresh` 分支。真正没有现成对应物的是另外三件：

1. **证据式判定（零 token）**：现有工具的完成语义都要求任务**自己正确表态**——退出码、哨兵文件、或声明式输出。科研脚本常常不表态（不打印完成关键词、不写约定产物、异常退出但结果其实可用），所以 quest 从日志尾关键词、退出码、产物新鲜度三个证据源给三态结论：`ok` / `suspect` / 失败。
2. **`suspect` 这个第三态**：Airflow 的任务状态是固定枚举，**不支持自定义状态，也不允许自定义 trigger rule**（社区里"warn 但不 fail"的需求官方答复是"做不到"）；Prefect 的 `allow_failure` 能表达"上游失败也让下游跑"，但它的语义在 2026 年仍在重构（区分"自己失败"与"被上游阻塞"），且默认行为与我们要的不一致。换句话说：**分支去连引擎，会把最难的那一层交给一个正在 churn 的 API。**
3. **AI 在环**：worker 一次性会话写总结（主对话零增长）、fixer 带预算自动修复、`suspect` 时让探针查证再由 AI 决定续跑还是停——这些是 LLM 时代才出现的东西，引擎生态里没有对应物。

再加上一条工程约束：quest 现在**零外部依赖**（一个 node 进程 + 文件）。Windmill/Hatchet 要 Postgres/Redis/Docker；Snakemake 官方在 2026 年仍把 Windows 用户推向 WSL；Prefect 是唯一 Windows 一等公民的候选，但要引入一个常驻服务。研究者的笔记本 + 要能直接分发，这两条比"更规范的实现"重要。

**结论**：把战斗力放在三件没有替代物的事情上；调度与 UI 保持手写，但保持在能被替换的规模（接缝只有三处：`dispatchJob`+`orchestrate`、`judge`+`extractMetrics`+`evalWhen`、`finishNode`）。哪天需要多机/多卡排队、跨天持久化编排、或给别人看的正式 UI，再按 KPI 做一次限时原型，而不是现在赌。

## 2. 为什么"疑似"不冻结下游，而是让 AI 裁决

`suspect` 代表"没找到完成证据"，不等于失败——可能是脚本没写日志，也可能真的没跑完。早先的实现把它等价于失败并冻结整条下游（保守），结果是一次误判就让整条链停摆等人。

现在的默认仍是 `any-fail`（保守），但节点/plan 头可声明 `freeze_on: hard-fail-only`：只有**真失败**（崩溃/启动失败/超时/取消/预检失败）才冻结；疑似则放行，同时推一条带探针指令的通知，让 AI 去看日志与产物、再决定续跑还是取消。**在脚本里硬编码这个判断太僵硬，而探针让中间裁决成为可能。**

## 3. 判定器为什么不把 quest 自己的文件当产物

`progress.md` / `research-state.md` / `plan.md` 都写在任务工作区里（也就是节点 cwd），而 `.md` 属于判定器的"文本产物"。后果是：节点运行期间**任何一次 `/api/status` 刷新都会重写 `progress.md`**，于是一个零产物的节点也被判成 `ok/artifact-fresh`——假 ok 会把真失败盖过去。所以这三类台账文件被显式排除在产物扫描之外（沙箱里复现过，修复后验证通过）。

## 4. 通知出口：provider 无关、默认关闭

quest 对外只有一个 HTTP 调用，`notify.kind` 三态：`off`（默认）/ `bridge` / `webhook`。**不内置任何 IM 桥**——桥是独立项目，能不能分发是它们自己的事。可靠性的重活（3 次退避重试、4xx 视为不可重试直接丢弃、失败落盘队列 2 分钟补发、超长消息保留头尾）在 quest 这一侧，与出口无关。图片产物直推只在 `bridge` 模式可用，其余模式明确提示不支持而不是静默丢弃。

## 5. 监督器为什么不做成 Windows 服务

quest 进程本身需要外部拉起来（服务无法监督自己）：任务侧崩溃存活是 quest 自己的机制，但进程死了就没人判定、通知、认领。

Windows 上的诱惑是 NSSM/服务或"不管用户是否登录都运行"的计划任务——**这两个都跑在 session 0，而 Store 版 WSL 在 session 0 里不可用**（`wsl.exe` 直接失败），quest 的 WSL 车道正是靠 `wsl.exe` 派发的。所以选择"登录时运行 + 每小时复查 + 不重复实例"的计划任务，配合一个自愈批处理（5 秒重起 + 端口单实例守卫 + 日志轮转）。代价是注销即停——这与 WSL 虚拟机随会话消失的事实一致，不是额外损失。

Linux 侧直接用 systemd 用户单元（`Restart=always` + 重启风暴保护），不要自己写守护。
